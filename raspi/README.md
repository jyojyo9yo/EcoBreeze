# EcoBreeze — 라즈베리파이 구현 (2026 경상국립대 AI 에너지 스마트홈 메이커톤)

`../EcoBreeze_final_logic_report.docx`의 절전 로직(① 쾌적대 파악 → ② 변동폭
최대화)을 라즈베리파이 하나로 전부 처리하는 구현. 센서 읽기, PMV/쾌적대 학습,
제어 판단, IR 송신, 웹 대시보드까지 전부 이 폴더 안에서 돈다.

대회 현장에 실제 에어컨이 없어서, **아두이노 + LED를 "에어컨 대역"으로 세워
시연한다.** 라즈베리파이가 계산한 컴프레서 on/off 판단을 실제 IR LED로 쏘고,
아두이노가 IR 수신모듈로 그 신호를 받아 LED를 켜고 끈다 — 신호가 물리적으로
전달되는 걸 눈으로 보여주는 구조다. 아두이노 배선/코드는 `../arduino/`.

실내온도는 여전히 잴 실제 방+에어컨이 없으므로 `config.SIMULATION_MODE = True`
(가상 열모델)로 로직을 검증한다. 반면 `config.DRY_RUN_IR = False`가 기본값 —
Pi→아두이노 IR 송신 자체는 실제로 나가야 시연이 되기 때문이다 (pigpio가 없는
개발 PC에서는 `ir_control.py`가 이를 감지해 자동으로 dry-run으로 내려간다).

## 파일 구성

| 파일 | 역할 |
|---|---|
| `config.py` | 핀맵/파라미터/모드 플래그 전부 |
| `pmv.py` | Fanger PMV/PPD 계산 + 목표 PMV에 대한 온도 역산 |
| `comfort_band.py` | ① 쾌적대 파악: 중심=PMV로 습도 반영 계산+override로 학습, 폭=설문으로 선택한 °C 값(자동학습 안 함) + 취침리듬보정 |
| `sensors.py` | SHT31 온습도 센서 (I2C, smbus2) |
| `ir_control.py` | pigpio 기반 IR 송수신. ①실제 에어컨 리모컨 학습/재생(향후용), ②대회 시연용 고정 NEC 프로토콜로 아두이노에 컴프레서 on/off 송신(`send_compressor`) |
| `power_monitor.py` | PZEM-004T (Modbus RTU) 전력 실측, tau_ac/돌입전류 보조 |
| `ac_simulator.py` | 실제 에어컨 없을 때 쓰는 가상 방 열모델 + 가속 시계 |
| `ecobreeze_main.py` | 상태머신 + ② 변동폭 최대화 제어 루프 (메인 진입점) |
| `dashboard.py` | 실시간 웹 대시보드 + 수동 제어 (취침시작/종료, override 시뮬레이션, 온도 민감도 설문) |
| `../arduino/ecobreeze_receiver/` | 아두이노 수신 스케치 — IR로 컴프레서 상태를 받아 LED로 표시 ("가짜 에어컨") |
| `../EcoBreeze_Logic_Design.md`, `../Config.h`, `../PMV.*` | ESP32/C++ 참고용 초안 (현재는 미사용, 방향성만 참고) |

## 대회 시연 구성 (3자 구조)

```
[브라우저 대시보드] <-- HTTP(폴링) --> [라즈베리파이: ecobreeze_main.py + dashboard.py]
                                              │
                                              │ IR (38kHz, 고정 NEC 프레임)
                                              ▼
                                   [아두이노: ecobreeze_receiver.ino]
                                              │
                                              ▼
                                   컴프레서 상태 LED (on=켜짐 / off=꺼짐)
```

### 배선 (라즈베리파이 쪽)

- IR LED(940nm, 2N2222로 스위칭) → GPIO18 (`config.PIN_IR_SEND`)
- (선택) IR 수신모듈 VS1838B → GPIO17 — 실제 에어컨 리모컨을 나중에 학습할 때만 필요, 이번 데모(아두이노 LED)엔 불필요

### 배선 (아두이노 쪽) — `../arduino/ecobreeze_receiver/ecobreeze_receiver.ino`

- IR 수신모듈(VS1838B 등) OUT → 디지털 핀 11
- 컴프레서 상태 LED(+저항 220~330Ω) → 디지털 핀 7
- (선택) 하트비트 LED → 디지털 핀 6 — 아두이노가 안 멈췄다는 걸 보여주는 용도, 없어도 무방
- 라이브러리 매니저에서 **IRremote**(Armin Joachimsmeyer, v4.x) 설치 후 스케치 업로드

IR LED를 아두이노의 IR 수신모듈 쪽으로 향하게 배치(또는 근접 배선)해야 신호가
잡힌다 — 실제 시연 부스에서는 두 기기를 가까이 놓거나 짧은 관/튜브로 감싸
주변 조명 간섭을 줄이는 걸 권장.

### IR 신호 설계 — 왜 "커스텀"인가

`ir_control.py`의 데모 경로(`send_compressor`)는 **프레임 구조(타이밍)는 표준
NEC 프로토콜을 그대로 쓰고, 그 안의 주소/커맨드 값만 우리가 정한 커스텀
값**이다.

```python
NEC_ADDRESS = 0xEB              # "EcoBreeze" — 실제 제조사 코드가 아니라 임의로 정한 값
NEC_CMD_COMPRESSOR_ON  = 0x01
NEC_CMD_COMPRESSOR_OFF = 0x02
```

- **왜 진짜 LG 등 실제 에어컨 프로토콜(예: `IRremoteESP8266`의 LG2)을 안
  썼나**: 실제 프로토콜은 체크섬 포함 확장 프레임이라 포팅 비용이 크고,
  검증할 실물 리모컨/오실로스코프가 없어 포팅해도 맞는지 확인할 방법이
  없다. 지금 이 아두이노+LED는 실제 에어컨이 아니라 "신호가 물리적으로
  전달된다"는 걸 보여주는 대역일 뿐이라, 실제 기기 프로토콜을 흉내 낼
  필요가 없다.
- **왜 그래도 NEC 프레임 구조는 표준을 따랐나**: 리더(9000/4500µs), 비트
  마크(562µs), 0/1 스페이스(562/1687µs) 같은 타이밍 자체를 새로 지어내면
  그것도 검증 근거가 없어진다. NEC는 공개적으로 잘 알려진 표준이고
  아두이노 `IRremote` 라이브러리가 디코더를 기본 내장하고 있어서, "인코딩/
  디코딩 로직은 검증된 표준을 그대로 재사용하고, 그 안에 실을 값(주소·
  커맨드)만 우리 것"으로 만들면 프레임 자체의 정확성 리스크는 없앨 수 있다.
- **검증 상태**: 8분짜리 시뮬레이션 세션에서 86회 on/off 토글이 아두이노
  LED에 매번 정확히 반영되는 것을 실행 테스트로 확인함.
- 실제 에어컨을 학습해 제어하는 경로(`learn_button`/`send`/
  `send_setpoint`)는 이것과 완전히 별개다 — 위 "실제 에어컨으로 전환할 때"
  섹션 참고.

### 실행

```bash
# 아두이노: IDE에서 ecobreeze_receiver.ino 업로드, 시리얼 모니터(115200)로 수신 로그 확인

# 라즈베리파이 터미널 1
python ecobreeze_main.py

# 라즈베리파이 터미널 2
python dashboard.py
```

브라우저로 `http://<라즈베리파이IP>:8080` 접속 (같은 기기면 `http://localhost:8080`).

1. **"취침 시작"** 버튼 클릭 → 가상 방(초기 29°C)이 시뮬레이션 시계로 빠르게
   흐르기 시작 (기본 60배속: 8시간 밤이 실제 약 8분)
2. 실내온도가 밴드 상한(hi)을 넘으면 Pi가 IR로 "컴프레서 ON"을 쏘고 **아두이노
   LED가 켜짐**. 온도가 다시 밴드 하한(lo)까지 내려가면 "컴프레서 OFF"를 쏘고
   **LED가 꺼짐** — 이후 실내온도가 다시 데워져 hi를 넘으면 또 켜지고, 를
   반복한다. 즉 LED는 "취침 시작~종료" 사이에 **한 번만 켜지는 게 아니라, 그
   동안 계속 실시간 컴프레서 상태를 따라간다** (8분짜리 데모 세션 기준 수십
   회 켜짐/꺼짐 반복 확인됨). 대시보드 로그에도 매번 `compressor_on`/
   `compressor_off` 이벤트가 찍힌다.
3. **"override: 더 시원하게(-1°C)"** 버튼을 눌러보면 — `personal_offset`(쾌적대
   중심)이 그 방향으로 즉시 이동하는 걸 확인 가능. 밴드 "폭"은 override로
   바뀌지 않는다 — 대신 **"온도 민감도 설문"** 패널의 민감함/보통/둔감함
   버튼으로 직접 정한다 (아래 참고)
4. **"온도 민감도 설문"** 버튼(민감함/보통/둔감함)을 눌러보면 — 밴드 폭이
   즉시 바뀐다 (민감함=±0.5°C 가장 좁음, 둔감함=±1.5°C 가장 넓음, 보통=±1.0°C
   기본값). 이 값은 PMV로 역산한 게 아니라 config.py에 직접 °C로 적혀
   있어서 숫자가 그대로 온도폭이다. 언제든(취침 중이 아니어도) 바꿀 수 있고,
   다음 계산부터 바로 반영된다
5. **"취침 종료"**를 누르면 (그 시점 컴프레서 상태와 무관하게) LED를 확실히
   끄고 세션을 마감, `night_log.csv`에 요약을 남긴다 — 이건 2·3번의 실시간
   변화와는 별개로 "기상 시 마무리 처리"일 뿐이다

`config.SIMULATION_MODE=True`인 동안은 `sensors.py`(SHT31/smbus2)와
`power_monitor.py`(PZEM/pyserial)가 실패해도 프로그램이 죽지 않고 그냥
"연결 안 됨"으로 넘어가도록 만들어뒀다 — 즉 **온습도 센서·전력계 없이도**
바로 시연 가능하다 (IR 송신 자체는 실제로 나가야 하므로 IR LED 배선은 필요).

## 실제 에어컨으로 전환할 때 (대회 이후)

지금 구조는 "Pi가 아두이노+LED에 컴프레서 on/off만 알려준다"는 데모용
고정 NEC 프로토콜(`ir_control.py`의 `send_compressor`/`send_nec`)이다.
실제 에어컨을 제어하려면 이것 대신 **리모컨을 학습해 재생하는 경로**
(`learn_button`/`send`/`send_setpoint`, 같은 파일에 이미 구현되어 있음)로
바꿔야 한다:

1. `config.py`에서 `SIMULATION_MODE = False`로 변경 (`DRY_RUN_IR`은 그대로 `False`)
2. 배선:
   - SHT31: SDA→GPIO2, SCL→GPIO3, 3.3V, GND (부품목록의 BME280을 쓸 경우
     `sensors.py`에 동일한 `.read() -> (temp_c, rh)` 인터페이스로 BME280 드라이버를
     추가해서 교체 — BME280은 ±0.5~1.0°C라 본 제품이 감지하려는 개인편향(약
     0.5°C)과 같은 자릿수이므로 정밀도가 아쉬우면 SHT31 권장)
   - IR 수신(VS1838B) → GPIO17, IR LED(2N2222로 구동) → GPIO18
   - PZEM-004T → USB-TTL 변환기로 연결 (콘센트형 에어컨이면 Tapo P110M
     스마트플러그가 활선 작업 없이 더 안전 — 이 경우 `power_monitor.py`를
     Tapo 로컬 API 호출로 교체 필요, 이 저장소엔 미포함)
3. `sudo pigpiod` 데몬 실행 (IR 송수신에 필요)
4. `python -c "from ir_control import IRControl; ir = IRControl(dry_run=False); ir.learn_button('cool_at_24')"` 같은
   식으로 실제 리모컨 버튼 학습 (몇 개의 `cool_at_XX` 온도 매크로 + `cool_off`
   + override 감지용 `temp_up`/`temp_down`)
5. `ecobreeze_main.py`의 `_set_compressor()`에서 `self.ir.send_compressor(on)`
   (데모용 NEC 고정신호) 호출을 `self.ir.send_setpoint(hi 또는 lo)`로 교체 —
   지금은 아두이노 LED 데모에 맞춰 on/off만 보내지만, 실제 에어컨은 설정온도
   재생 방식(4.4절 밴드 로직)이 필요하다
6. 서보모터(SG90) 백업: IR 캡처가 실패하는 기종이면 `ir_control.py` 대신
   서보로 리모컨 버튼을 직접 누르는 방식으로 교체 필요 (이 저장소엔 미포함,
   부품목록 리스트 17번 참고)

## 알려진 단순화 (v1)

- 지금 대회 시연 경로(`send_compressor`)는 실제 에어컨 프로토콜이 아니라
  **아두이노 전용 고정 NEC 코드**다. 실제 에어컨 제어는 `send_setpoint()`
  경로(아래)를 써야 한다.
- `send_setpoint()`는 실제 IR 프로토콜을 디코딩하지 않고, 미리 학습해둔
  `cool_at_23`, `cool_at_24`... 매크로 중 가장 가까운 것만 재생한다. 세밀한
  임의 온도 제어가 필요하면 기종별 프로토콜 인코딩으로 교체 필요.
- PZEM-004T는 ~1Hz 갱신이라 돌입전류(1~2초 파형)를 정밀하게 못 잡는다 —
  `power_monitor.sample_inrush()`는 근사치만 제공.
- PMV 파라미터(`PMV_CLO=1.0`, `PMV_MET=0.75`, `PMV_CENTER_TARGET=-0.2`)는 전부
  실측 전 가정치다. `../실내 온도 취침.csv` 등 기존 실험 데이터로 역보정 필요.
  (반면 `ac_simulator.py`의 냉각/승온 속도는 이미 이 CSV에서 직접 측정한
  값으로 교체됨 — `config.py`의 `SIM_COOL_RATE_C_PER_MIN`/`SIM_WARM_RATE_C_PER_MIN`
  주석 참고.)
- 기동 판단(`_control_cycle`)은 순수 반응형이다 — `t_room`이 `hi`에 실제로
  도달해야 켠다. `HYST_IN_C`/`HYST_OUT_C`(0.1°C)는 `tau_ac` 지연을 예측해서
  미리 켜는 로직이 아니라, 경계 근처 센서 노이즈로 인한 on/off 떨림을 막는
  대칭적 여유일 뿐이다 (켤 때 `hi-0.1`, 끌 때 `lo+0.1` 양쪽 다 적용).
  그래서 `tau_ac`(약 3분) 동안 냉방 효과 없이 온도가 계속 오르면 `hi`를
  살짝 넘는 오버슈트가 생길 수 있는데, 크기는 `warm_rate × tau_ac` ≈
  0.06°C/min × 3분 ≈ 0.18°C 수준(HYST_OUT_C만큼 빼면 실질 0.1°C 안팎)이라
  밴드 반폭(±0.5~1.5°C)에 비해 작고 PPD 곡선도 완만해 체감 영향은 미미할
  것으로 본다. 지금 `ac_simulator.py`는 이 지연 구간을 "온도 변화 없음"으로
  단순화해서 시뮬레이션엔 오버슈트 자체가 안 나타난다. 실측 후 체감된다면
  기울기 기반 예측 기동을 새로 짜기보다 `HYST_OUT_C`를 0.2~0.3°C로 올리는
  쪽이 더 간단한 해결책이다.
- 검증 (같은 673분(11시간 13분)짜리 밤, `../실내 온도 취침.csv` 기준):
  - **참고용 비교**(실측 vs EcoBreeze 1일차 설문 기본값): 실측 24회 vs 시뮬레이션
    8회. 다만 이건 **평균온도 조건이 다르다** — 실측 steady-state 평균은
    24.60°C인데 EcoBreeze 쪽 중심은 PMV 계산으로 약 25.3°C가 나와서, 사이클이
    준 이유가 "폭을 넓혀서"인지 "평균이 더 따뜻해서"인지 섞여 있다.
  - **동일 중심 비교** (폭 효과만 분리): 중심을 실측 평균(24.60°C)으로 양쪽
    다 고정하고 폭만 좁게(±0.3°C, 네이티브 데드밴드 수준) vs 넓게(±1.0°C,
    설문 "보통") 바꿔서 같은 시뮬레이터로 비교 → **41회 vs 11회**. 이게 평균온도
    변화를 배제하고 "폭을 넓히면 기동이 준다"만 순수하게 보여주는 수치다.
  - 두 비교 다 개인 학습(override, 설문)이 하나도 없는 콜드스타트 기준.
- 취침/기상 트리거는 v1에서 파일 트리거(대시보드 버튼)로 처리 — 실제 제품화
  시 앱/물리버튼으로 교체.

## 요약

- **전략**: ① 쾌적대 파악 → ② 그 안에서 아무 것도 안 하고 변동폭을 최대한
  써서 컴프레서 기동 횟수를 줄임.
- **쾌적대 중심**: 습도 반영 PMV 역산값(매 사이클 재계산) + override로 학습된
  `personal_offset` + 수면리듬 보정. 학습이 끝난 뒤에도 PMV 역산 자체는 계속
  돈다.
- **쾌적대 폭**: PMV로 역산하지 않고 대시보드 설문(민감/보통/둔감 →
  ±0.5/±1.0/±1.5°C)으로 직접 설정. override로 자동 학습하지 않음 —
  "어디가 편한가(중심)"와 "얼마나 민감한가(폭)"는 성격이 달라 학습 방식도
  분리.
- **제어**: `t_room`이 `hi`에 도달하면 켜고 `lo`에 도달하면 끄는 순수 반응형
  히스테리시스. 예측 기동 없음 — 있어도 오버슈트가 작아(≈0.1~0.18°C) 실익이
  적음.
- **절감 메커니즘**: 평균온도 상승 + 무효 냉방구간(기동지연) 감소가 "폭 확대"
  하나의 조작에서 동시에 발생 (이중계산 금지). 통제 실험(같은 중심, 폭만
  변경)으로 폭 효과만 분리하면 41회→11회.
- **하드웨어**: 실제 에어컨/방이 없어 아두이노+LED를 가짜 에어컨으로, 실측
  데이터로 보정한 가상 방 모델을 시연에 사용. 라즈베리파이 하나가 센서·로직·
  IR 송신·대시보드를 전부 담당.
- **아직 안 된 것**: 하드웨어 실측(pigpio/실제 센서/전력계/아두이노 컴파일
  전부 미검증), 실제 에너지 절감률(%) 미측정, PMV 파라미터(clo/met)
  미보정.
